# Packaging Loom for Linux

Everything a Flatpak build needs. This folder ships in the public release
snapshot, so the Flathub repository holds only a manifest that points here.

## Why Flatpak, and why not a frozen build

The roadmap's packaging plan says freezing is the common substrate and every
platform starts there. That is right for the `.exe` and the `.app` and wrong
for Flatpak: the runtime brings a real Python, so Loom is installed **from
source** and PyInstaller is not involved on Linux at all.

Three consequences, and they are the reason this folder is small:

- **No Linux `loom.spec`.** The capture and hotkey backends load through
  `importlib`, which static analysis cannot see — the reason `loom.spec` names
  them as `hiddenimports`. Unfrozen, that problem does not exist.
- **APM works.** `sys.frozen` stays unset, so `loom/entry.py` takes its
  interpreter branch and `-m tools.apm_counter` runs. On Linux, APM is a child
  process; it is the one thing a frozen Linux build could not have started,
  because `entry.MODES` has no `apm` mode and `argv_for` raises without one.
- **Writable data still leaves the tree.** `paths.installed()` asks whether
  `PROJECT_ROOT` is writable rather than whether PyInstaller built this, so
  `/app` being read-only is enough to move captures to the data directory.

Bazzite's store is **Bazaar**, a front-end over Flathub. There is no separate
Bazzite queue: publishing to Flathub is what puts Loom in that store, and the
same artifact serves Fedora, Ubuntu, Arch, SteamOS and Nobara.

## The files

| File | What it is |
|---|---|
| `io.github.gwaihirf22.loom_AOE.yml` | The Flatpak manifest |
| `io.github.gwaihirf22.loom_AOE.metainfo.xml` | AppStream metadata — what a software centre shows |
| `io.github.gwaihirf22.loom_AOE.desktop` | The desktop entry |
| `io.github.gwaihirf22.loom_AOE.png` | 256×256 icon, generated by `python -m tools.make_icon` |
| `loom.sh` | The `/app/bin/loom` entry point |
| `generate-deps.sh` | Regenerates `python3-deps.yml`; run when `requirements.txt` changes |
| `python3-deps.yml` | **Generated.** Pinned wheels — never hand-edit |

**The app id appears in five places and they all have to agree**: the manifest
`app-id`, the metainfo `<id>`, the `.desktop` basename, the icon basename, and
`loom.entry.DESKTOP_ID`. The last one is what `loom_app.py` hands to Qt's
`setDesktopFileName`, and it is what associates a running window with the
entry that carries the icon.

## Building it

`python3-deps.yml` is not committed until `generate-deps.sh` has been run on
Linux — it needs `pip download` against the runtime's own Python version.

On an atomic distribution (Bazzite, Silverblue) `flatpak-builder` is not a
host binary and layering it costs a reboot. `org.flatpak.Builder` is the same
program packaged as a Flatpak, and the commands below use it.

**Add a `--user` flathub remote first, or the installs do nothing and say so
only in passing.** Bazzite ships flathub as `system,filtered`; there is no
`--user` counterpart until one is added, and `flatpak install --user flathub
<ref>` then prints `error: No remote refs found for 'flathub'` and **exits
0**. Nothing is installed and the return code reports success.

```sh
flatpak remote-add --user --if-not-exists flathub \
    https://dl.flathub.org/repo/flathub.flatpakrepo

flatpak install --user flathub org.flatpak.Builder
flatpak install --user flathub org.kde.Platform//6.11 org.kde.Sdk//6.11
flatpak install --user flathub com.riverbankcomputing.PyQt.BaseApp//6.11

cd packaging/linux
./generate-deps.sh                      # once, and after any requirements change

cd ../..
flatpak run org.flatpak.Builder --user --install --force-clean \
    build-dir packaging/linux/io.github.gwaihirf22.loom_AOE.yml
flatpak run io.github.gwaihirf22.loom_AOE
```

A single-file bundle for the GitHub Release:

```sh
flatpak run org.flatpak.Builder --repo=repo --force-clean \
    build-dir packaging/linux/io.github.gwaihirf22.loom_AOE.yml
flatpak build-bundle repo Loom-X.Y.Z-x86_64.flatpak io.github.gwaihirf22.loom_AOE
```

Validate the metadata before publishing either:

```sh
appstreamcli validate io.github.gwaihirf22.loom_AOE.metainfo.xml
desktop-file-validate io.github.gwaihirf22.loom_AOE.desktop
```

## The permissions, and the argument for them

Loom asks for **one** privileged thing. Every OS-facing feature routes through
the X server the game already lives on:

| Call | Where |
|---|---|
| `XGetImage` on the game's window | `loom/capture/x11.py` |
| `XQueryTree` to find that window | `loom/capture/x11.py` |
| `XGrabKey` for global hotkeys | `loom/hotkeys/x11.py` |
| `XISelectEvents` (XInput2) for APM | `tools/apm_counter.py` |
| `XShapeGetRectangles` for click-through | `loom/passthrough.py` |
| `QT_QPA_PLATFORM=xcb` | `loom_overlay.py` |

Wayland has no API for reading another window's pixels or grabbing a key
globally — by design — so there is no portal route to any of it, and
`docs/platform-support.md` records the desktop-screenshot route returning
black. The game runs under XWayland; Loom must be on the same X server, which
is why `--socket=fallback-x11` will not do.

Flathub labels X11 apps *"potentially unsafe: uses a legacy windowing
system"*. That is accurate and unavoidable for a screen-reading tool.

**`--device=input` is NOT requested.** Nothing in the tree touches
`/dev/input`, evdev, uinput or pynput; APM is XInput2 raw events on the root
window, already covered by the X11 socket. `loom/hotkeys/__init__.py` explains
the design: Loom is handed the few combinations it grabbed and cannot learn
about a key it did not ask for.

The Steam holes are read-only and scoped to AoE2 DE's app id (813780) rather
than to Steam as a whole. Loom opens one save folder, after a match has ended,
and never writes to it. A library on a second drive is not covered and cannot
be — see `LOOM_RECORDS_DIR` and `docs/install-linux.md`.

## Submitting to Flathub

Change the `loom` module's source from `dir` to the release tarball:

```yaml
    sources:
      - type: archive
        url: https://github.com/gwaihirf22/loom_AOE/archive/refs/tags/v1.0.7.tar.gz
        sha256: <sha256sum of that tarball>
```

Then fork `flathub/flathub`, add the manifest, and open a pull request against
the **`new-pr`** branch — not `master`. `bot, build io.github.gwaihirf22.loom_AOE`
in a comment runs the build.

Flathub's guidelines state that submission pull requests must not be
generated, opened or automated using AI tools or agents. The manifest and
metadata here are ordinary source files in this repository; the submission
itself is written and opened by hand.
